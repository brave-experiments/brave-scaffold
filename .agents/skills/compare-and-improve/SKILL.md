# Compare and improve

Produce one result that better meets the stated requirements, using supported
strengths from either alternative and fixing supported gaps. A blend is useful
only when it improves the result.

## Establish the comparison

Identify the intended outcome, requirements, two alternatives, comparison scope,
and selected target. Assess both against the same criteria. If the target is
unspecified and choosing it materially changes the work, clarify the choice
while continuing independent comparison. Wait for that choice before editing
either alternative.

For branches, establish the relevant base and revisions so unrelated history
does not distort the feature comparison. For written work, identify the versions
and intended audience or use. Separate requirements from either alternative's
proposed choices.

## Assess both alternatives

Review each as a whole, including strengths, weaknesses, gaps, assumptions,
tradeoffs, and relevant failure paths. Inspect enough surrounding context to
understand how its parts work together. Identify requirements and failure paths
that both miss; agreement does not establish correctness.

Judge correctness, completeness, and fitness for the requirements. Ignore who
or what produced either alternative. Give no preference to the current branch,
the longer document, or an approach's origin.

Ground material findings in evidence. For claims about existing software
behavior, inspect the relevant code and use focused checks where appropriate.
Do this even when the alternatives are written proposals. Distinguish verified
facts from proposals, assumptions, and unresolved questions. Cite the relevant
revision, file and lines, document section, or check result so the evidence is
traceable to the correct alternative. State when evidence is missing or a check
cannot be run.

## Strengthen the selected result

Use the comparison to decide what to retain, adapt, replace, or omit in the
user's selected branch or document. Incorporate compatible strengths and address
supported gaps, including gaps shared by both alternatives. Resolve conflicting
choices against the requirements before combining them. Keep a better approach
intact when blending would weaken it; explain material choices with evidence.

Complete the requested improvements within the authorized scope. A comparison
does not authorize unrelated changes or external actions. For a review-only
request, provide findings and recommended changes without editing either
alternative. If a material conflict depends on a missing user decision, continue
independent work and leave that change pending.

## Verify and report

Check the resulting code or document against the requirements and material
findings. For code, use focused checks of affected behavior and relevant failure
paths, including interactions introduced by combined changes. For documents,
check factual support, requirement coverage, and consistency after revision;
do not present proposed behavior as implemented or verified.

Report what changed, the evidence behind key decisions, checks performed and
their results, and unresolved limitations. For review-only work, report the
recommended result and supporting findings instead of claiming improvements
were applied.
